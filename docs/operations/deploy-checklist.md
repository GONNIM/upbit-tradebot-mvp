# 배포 체크리스트 (systemctl restart 기반)

**목적**: `systemctl restart tradebot` 후 배포가 완결됐다고 판단하는 기준을 명시.
과거 사고 재발 방지용 최소 체크리스트.

---

## 배포 완결 기준

`systemctl restart tradebot` 만으로는 배포 완결이 아니다. **엔진 세션 개시 확인까지가 배포 완결**이다.

Streamlit 서비스는 재시작 후 웹 서버만 대기 상태로 들어가고, 실제 트레이딩 엔진(`engine/live_loop.py`)은 세션 진입(대시보드 접속 또는 `[AUTO-RESUME]` 트리거) 시에만 시작된다. 서비스가 `active (running)`이어도 엔진이 시작되지 않으면 트레이딩 공백이 발생한다.

### 배포 완결 확인 로그 시퀀스

`journalctl -u tradebot` 에서 다음 로그가 **모두 출현**해야 배포 완결:

1. `🚀 [UPBIT_MATCH] Clock-based REST Reconcile 모드 시작`
2. `✅ CandleClock 초기화 | interval=minute1 | interval_sec=60`
3. `✅ [WARMUP] REST 데이터 로드 완료 | bars=200`
4. `✅ Indicator seeded (separate EMA) | BUY: ... | SELL: ... | base=...`
5. `✅ Warmup 완료 | bars=200`
6. `🚀 [CLOCK-LOOP] 시작 - 1초마다 폴링, 봉 확정 시 REST Reconcile`
7. 이후 봉 확정 시각에 `⏰ [CLOCK-CLOSE] 봉 확정 감지` + `✅ [CONFIRMED] 봉 처리 완료`

7번까지 확인되어야 실제 트레이딩이 재개된 것.

### 오류 부재 확인

같은 구간(`--since '<restart_ts>'`)에 다음 로그 **부재** 필수:
- `Traceback` / `Error` / `Exception`
- `OperationalError` / `no such column`
- `CRITICAL` / `POLLUTED`

### 24h 실측 타이머 기점

기점 = **엔진 세션 개시 시각** (위 5번 `Warmup 완료` 또는 6번 `CLOCK-LOOP 시작` 시각). systemd `Started` 시각이 아님.

### WO-6 배포 이후 감사 시각 표시 변화 예고 (운영 주석)

WO-6이 배포되면 `candle_clock.get_closed_ts`의 반환값 의미가 재정의되어,
감사 로그(`audit_buy_eval`, `audit_trades`)와 대시보드에 표시되는 봉 시각
(`bar_time`)이 개편 이전보다 60초 앞당겨 보이게 됨. 이는 실제 시장 마감
시각(Upbit 봉 시작 시각)에 맞춘 정상 표기이며, 매매 판단이나 발주 시점
자체가 앞당겨지는 것은 아님. 배포 시점을 기준으로 이 표시 변화를 운영자와
사용자에게 사전 안내할 것.

### 2026-08-30 WO-6 감사 누락 수정 배포 (v1.2026.08.30.1633)

- 배경: WO-6 20시간 실측에서 실시간 판단 봉 44건이 audit_buy_eval 에 저장
  되지 않음(케이스 B 안정화 확정 경로에 집중). 로그 기준 실시간 커버리지는
  100% 였으나 감사 기준은 88.15%.
- **결함 명칭 정정 (2026-08-30 사용자 지시 반영)**: 이 결함은 "판단 누락"
  이 아니라 **"이중 판단 후 기록 소실"** 이다. 케이스 B 확정 봉이 두 번
  진입하여 봉당 1회 원칙이 침해되고 있었고, 첫 진입의 audit 가 두 번째
  진입의 처리와 상호작용하여 소실됐다. WO-6 이 명시적으로 도입한 봉당 1회
  원칙(`_evaluated_bar_ts` 검사)이 실제 실행에서 침해되는 상태였다는 사실
  자체가 이 사고의 핵심이다.
- 원인: `last_bar_ts` 가 두 곳(`strategy_engine.py:595`,
  `live_loop.py:1265/1319`)에서 판단·감사 이전에 갱신되어, 같은 봉의 두 번째
  진입에서 `is_new_bar=False` 로 조기 반환되고 audit 저장이 스킵됨. 두 번째
  진입 자체가 봉당 1회 원칙 침해의 증거였다.
- 수정: `last_bar_ts` 는 `strategy_engine` 안에서 판단·감사·주문 완료 이후
  `_register_evaluated_bar` 뒤에서만 갱신. `live_loop.py:1265`, `1319` 갱신
  제거. 중복 방지는 봉당 1회 검사(`_evaluated_bar_ts`)가 담당.
- 진단 로그 추가: `[ENGINE-ENTRY]`, `[ENGINE-SKIP-DUP]` (모두 INFO 승격).
- 회귀 테스트 5건 신설 (총 132/132 통과).
- 안착 판정 조건 2(총 지표 반영 커버리지 90%)의 대리 지표 오류 정정:
  이번 수정으로 감사 기준과 로그 기준 실시간 커버리지가 일치할 것으로 예상.

### 2026-08-30 배포 후 확인 1과 2 결과 (사용자 지시 반영)

**확인 1: RETRY 경로 재평가 모드 전환 판정**

RETRY 경로(`live_loop.py:1318`)는 첫 CLOCK-CLOSE 에서 확정 실패한 봉을
뒤늦게 확보하는 경로이며 그 봉은 아직 지표에 반영되지 않은 상태이다. 재평가
모드(`backfill_mode=True`) 로 전환하면 지표 갱신 후 원상 복구되어 close 가
영구 반영되지 않는다. 따라서 실시간 모드(`backfill_mode=False`) 유지가 맞고,
`last_bar_ts` 갱신 위치 이동만으로 충분하다.

**확인 2: 1265줄 제거의 파급 점검**

`engine.last_bar_ts` 를 읽는 지점 전수(886, 929, 1441~1443, 1486~1496,
strategy_engine.py:267)를 검토한 결과, 엔진 내부 갱신만으로 모두 정상 동작
한다. 재시작 직후 첫 봉은 WARMUP 초기값 기준 정상 진입, 무거래 건너뛰기
직후는 `last_bar_ts` 갱신 없이 다음 봉 정상 진입.

### 2026-08-29 WO-6 안착 판정 (조건 2 정정)

WO-6 20시간 실측에서 조건 2(총 지표 반영 커버리지 90%)가 감사 기준 88.15%
로 미달했으나, 로그 기준 100.00% 이 실질 실시간 판단이 모든 봉에 도달했음을
증명했다. 감사 저장 경로의 결함(WO-1 시절부터 존재)이 대리 지표 오류의
원인이었으며, 2026-08-30 수정 배포로 감사 경로가 정상화된다.
