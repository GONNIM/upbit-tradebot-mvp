**전제**: WO-6 안착 판정 완료 (2026-08-30 실측 로그 기준 실시간 커버리지 100%)

## 1부. 감사 누락 48봉 원인 조사 (WO-2 구현 착수 전 필수)

### 1.1 누락 봉 케이스별 분류

WO-6 20시간 실측에서 로그 기준 실시간 판단은 100%(405/405)였으나 감사 기준은
88.15%(357/405)로 48봉이 누락됐다. 누락 봉을 확정 케이스별로 분류했다.

| 확정 케이스 | 누락 봉 수 | 비율 |
|---|---|---|
| 케이스 A FAST (다음 봉 존재 즉시 확정) | 4 | 8.3% |
| 케이스 B 안정화 확정 | **44** | **91.7%** |
| 케이스 C 재시도 성공 | 0 | 0% |
| F1/F1b NO_TRADE | 0 | 0% (해당 없음, 무거래 봉은 모집단 밖) |

**핵심**: 누락 44봉이 케이스 B 안정화 확정 경로에 집중돼 있다. 사용자 지시대로
케이스 B 확정 봉의 감사 기록 경로부터 확인했다.

### 1.2 표본 3봉 로그 흐름과 분기 지점

**표본 1: 2026-08-30 03:42 봉**

```
03:43:00 [CLOCK-CLOSE] 봉 확정 감지 | ts=2026-08-30 03:42:00 KST
03:43:05 [RECONCILE] 케이스 B 첫 진입 (5초 안정화 대기) | ts=03:42:00 | close=687
03:43:10 [RECONCILE] 케이스 B 안정화 확정 ✅ | ts=03:42:00 | close=687
03:43:10 [REST] 최신 확정 봉 ✅ | ts=03:42:00
03:43:10 ✅ [CONFIRMED] 봉 처리 완료 | ts=03:42:00 | close=687.0
```

`[CONFIRMED] 봉 처리 완료` 로그(`engine/live_loop.py:1267`)는 남았지만
`strategy_engine`의 `Bar#XXX ts=... action=...` 로그가 없다. 즉
`engine.on_new_bar_confirmed`가 호출된 뒤 내부에서 조기 반환(early return)됐다.

**표본 2와 3 (03:52, 04:00 봉)**도 동일 패턴이다. `[CONFIRMED]` 로그는 있고
`Bar#XXX` 로그는 없다.

**분기 지점 코드 줄 번호 추적**

`engine/live_loop.py:1262 engine.on_new_bar_confirmed(bar, local_series,
diff_summary)` 호출 이후, `strategy_engine.on_new_bar_confirmed`가 조용히
반환할 수 있는 지점은 세 곳이다.

| # | 위치 | 조건 | 로그 |
|---|---|---|---|
| A | `strategy_engine.py:566~568` | `not bar.is_closed` | `logger.error(f"[ENGINE] 미확정 봉 거부 \| {bar.ts}")` |
| B | `strategy_engine.py:573~576` | `not backfill_mode and not self.is_new_bar(bar)` (`bar.ts == self.last_bar_ts`) | `logger.debug(...)` — INFO 레벨에서 미표시 |
| C | `strategy_engine.py:650~657` | `not backfill_mode and bar.ts in self._evaluated_bar_ts` (WO-6 봉당 1회 검사) | `logger.info(...)` — 표시됨 |

- **A**: `bar.is_closed=True`로 항상 설정(`live_loop.py:1256`)이므로 해당 없음.
- **C**: 로그가 `INFO` 레벨이므로 발생 시 로그에 남아야 한다. 표본 3봉 모두 이
  로그가 없다. **C는 원인 아님**.
- **B**: `logger.debug`이므로 INFO 레벨 서버에서는 로그가 나오지 않는다.
  이것이 유력한 조기 반환 지점이다.

**가설: `is_new_bar(bar)` 검사가 False를 반환한다**

`bar.ts`가 `self.last_bar_ts`와 같은 상황이다. `live_loop.py:1265`가 CONFIRMED
로그 직전에 `engine.last_bar_ts = closed_ts`로 갱신한다. 만약 같은 봉이 두 번
`on_new_bar_confirmed`에 진입하면 두 번째 진입에서 이 검사에 걸린다.

케이스 B 안정화 확정 흐름에서 두 번 진입할 수 있는 경로:
- `[RECONCILE] 케이스 B 안정화 확정 ✅` 로그(`03:43:10`)와 함께 `fetch_confirmed_candle`
  이 확정 봉을 반환.
- 이후 `reconcile_series` 실행. 이때 다음 봉의 CLOCK-CLOSE 처리에서 REST 재조회
  결과 같은 봉이 changed로 감지되어 `on_new_bar_confirmed`에 두 번째 진입할 수
  있다. 첫 진입에서 이미 `last_bar_ts`가 갱신됐다면 두 번째 진입은 `is_new_bar
  = False`로 조기 반환. 그런데 이 경우 audit는 첫 진입에서 이미 저장됐어야.

**대안 가설: `fetch_confirmed_candle` 반환값 처리 순서**

`live_loop.py:965~992` 확정 봉 결과 분기 흐름 재검토. 케이스 B 안정화 확정 시
`fetch_confirmed_candle`이 `pd.Series` 반환 → `rest_df.loc[closed_ts] =
confirmed_row` 실행 → `reconcile_series` 실행. 이 흐름에서 어떤 조건에 의해
`on_new_bar_confirmed` 호출 없이 `[CONFIRMED]` 로그가 나올 수는 없다. CONFIRMED
로그는 반드시 `on_new_bar_confirmed` 호출 직후에 나온다(`live_loop.py:1262~1267`).

**결론**: `on_new_bar_confirmed`가 호출은 됐지만 내부 조기 반환(가설 B, `is_new_bar`
False)이 유력하다. 정확한 확인은 임시로 라인 575의 로그를 `debug`에서 `info`로
승격해 재관측하는 것이 가장 확실하다.

### 1.3 WO-6 도입 vs WO-1 유래 판별

사용자 지시대로 WO-1 시절 감사 커버리지와 비교했다.

| 배포 상태 | 관측 기간 | 실시간 판단 봉 | 총 감사 봉 |
|---|---|---|---|
| WO-1 (배포 전 24h) | 08-28 19:30 ~ 08-29 19:29 | **592** | **622** |
| WO-6 (이번 20h) | 08-29 19:32 ~ 08-30 15:40 | 358 | 358 |

**중요 관측**: WO-1 시절에도 실시간(592)과 총 감사(622)의 차이 30봉이 있었다.
이는 실시간 판단은 없지만 BACKFILL만 있는 봉 30개가 있었다는 뜻이다. 반면
WO-6 이후에는 실시간과 총 감사가 동일(358)하다. BACKFILL only 경로가 사라졌다.

**판별 결론**: 감사 저장 실패 자체는 WO-1 시절부터 있던 결함이다. 다만 WO-6이
`is_new_bar` 검사의 진입 빈도를 바꾼 것으로 보인다. WO-6의 `get_closed_ts` 재정의
로 `closed_ts` 의미가 "방금 확정된 봉"으로 통일되면서, `last_bar_ts` 갱신 순서와
새 진입 판정 사이의 상호작용이 미세하게 달라졌을 수 있다.

**서버 WO-1 커버리지가 이전 조사에서 81.4%였고 이번 배포 직전 24시간이 592/(추정
Upbit 봉 수)로 계산되어야 정확한 비교가 가능하나, 실측 시점에 배포 직전 Upbit
원본 봉 수를 별도로 확보하지 않았다.** 이 부분은 별도 조사가 필요하다.

**핵심 판단**: 감사 누락은 WO-6이 새로 만든 결함이 아니며, WO-1 이전부터
존재해 온 감사 저장 경로의 미묘한 결함이다. WO-6 배포 자체를 롤백할 근거는
없다.

### 1.4 수정안 (구현은 승인 후)

**목표**: 매매 판단이 실행되는 모든 경로에서 감사 기록이 반드시 함께 실행되는
구조.

**수정안 A: `is_new_bar` 로그 승격 (진단 우선)**

- `strategy_engine.py:575 logger.debug` → `logger.info`로 승격.
- 실제로 조기 반환이 얼마나 자주 발생하는지 실측 확인.
- 배포 후 24시간 관측으로 원인 특정.

**수정안 B: 실시간 확정 봉 진입 시 audit 강제 저장**

- 아이디어: `is_new_bar` False로 조기 반환하기 전에 `_record_audit_log`를 한 번
  더 확인. 이미 저장된 봉이면 스킵하되, `INSERT OR REPLACE`(UPSERT)로 안전
  보장.
- `services/db.py insert_buy_eval`은 이미 `INSERT OR REPLACE`로 UNIQUE 인덱스
  `(ticker, bar_time)` 기준 UPSERT를 사용하므로 중복 걱정 없음.

**수정안 C: `last_bar_ts` 갱신 시점 조정**

- 현재: `live_loop.py:1265` CONFIRMED 로그 직전에 갱신.
- 대안: `strategy_engine.on_new_bar_confirmed` 안에서 audit 저장 이후에 갱신.
- 이렇게 하면 audit 저장 실패 시 `last_bar_ts`가 갱신되지 않아 다음 진입이
  재시도 가능.

**권장 순서**:
1. 먼저 수정안 A(로그 승격)를 배포하여 실측 원인을 특정한다.
2. 원인이 특정되면 수정안 B 또는 C 중 적합한 것을 채택한다.

**주의**: 이 수정은 WO-6과 별도 커밋으로 진행한다. WO-2 재적용 구현 착수 전에
반드시 완료해야 한다.

### 1.5 종결 (2026-08-31 16:38:32 KST 24시간 실측 통과)

수정안 A와 C가 결합된 형태의 단일 수정(커밋 `5ab50cf`, `v1.2026.08.30.1633`)이
2026-08-30 16:35에 배포됐다. 이 수정은 다음 세 가지를 함께 반영한다.

- `strategy_engine.py`의 `last_bar_ts` 갱신을 판단·감사·주문 완료 이후로 옮겼다.
  기존에는 버퍼 추가 직후에 갱신되어 두 번째 진입에서 조기 반환됐다.
- `engine/live_loop.py`의 두 곳(`CLOCK-CLOSE` 처리와 재조회 성공 경로)에 있던
  `engine.last_bar_ts` 갱신을 제거했다. 중복 방지는 `_evaluated_bar_ts` 봉당 1회
  검사가 담당한다.
- 엔진 입구 진단 로그(`[ENGINE-ENTRY]`)와 중복 스킵 로그(`[ENGINE-SKIP-DUP]`)를
  `INFO` 레벨로 승격했다. 이후 재발 감지가 가능하다.

배포 다음 날인 2026-08-31 16:38:32 KST에 배포 시각 기준 24시간 실측을 마쳤다.
결과는 다음과 같다.

| 검증 항목 | 결과 |
|---|---|
| Upbit 원본 거래 봉 (분모) | 711봉 |
| `audit_buy_eval` price NOT NULL distinct 봉 | 611봉 |
| `audit_sell_eval` price NOT NULL distinct 봉 | 100봉 |
| 감사 합집합 distinct 봉 (분자) | 711봉 |
| **판단 커버리지** | **711 / 711 = 100.00%** |
| 봉당 감사 판단 횟수 | 전 봉 1회 (`audit_buy_eval` 613/613, `audit_sell_eval` 101/101) |
| 초과 봉 (감사 있음, Upbit 없음) | 0봉 |
| 거짓 `CRITICAL` | 0건 |
| `POLLUTED` | 0건 |
| 실주문 감사 정합 | 5/5 정합 (오차 ≤ 2원) |

시간대별로도 모든 시간대에서 커버리지 100%가 유지됐다. 케이스 A(즉시 안착)
379봉과 케이스 B(BACKFILL 재평가 후 안착) 331봉을 합쳐 확정 봉 710봉, 무거래
분류 741봉으로 총 봉 이벤트 1451봉이 CLOCK-CLOSE 로그 총수와 정확히 일치한다.

엔진 진입 로그 관점에서는 2회 진입 봉 326건과 3회 진입 봉 2건이 관측됐으나,
감사 행은 마지막 실시간 판단(`backfill=False`)에서만 저장되어 봉당 1건 원칙이
유지됐다. BACKFILL 재평가 진입은 `_register_evaluated_bar` 등록 대상이 아닌
설계이므로 두 번째 실시간 진입이 첫 진입으로 잡혀 감사에 저장되는 흐름이며,
5ab50cf 커밋의 회귀 테스트 5건(총 132/132 통과)이 이 흐름을 검증한다.

**종결 근거**: 위 수치가 종결 근거다. "이중 판단 후 기록 소실" 결함은 재발하지
않았고, WO-6 안착 판정 조건이 실측으로 확정됐다. WO-2 재적용 착수 조건이
충족됐다.

## 2부. WO-2 재적용 설계안

### 2.1 설계 원칙 (기 승인 §6 재확인)

- 모든 봉은 실시간 평가를 받는다. 확정 여부와 무관하다.
- 매매 결정이 나온 봉은 확정 조건이 충족될 때까지 발주를 지연한다.
- 지연 최대 시간을 두어 무한 대기를 방지한다.
- BACKFILL은 지연 발주를 대신하지 않는다. BACKFILL은 지표 갱신과 감사 로그만
  담당한다.
- 확정된 종가로 유효성 확인 한 번만 실행. 재판정 없음.

### 2.2 지연 상한 산정 (이번 24시간 실측 입력)

케이스별 확정 소요 시간을 실측했다.

| 케이스 | 관측 건수 | CLOCK-CLOSE → 확정까지 소요 |
|---|---|---|
| A (다음 봉 존재 즉시 확정) | 54 | 약 5~15초 (다음 봉 REST 반영 대기) |
| B (5초 안정화 확정) | 352 | 약 10~15초 (첫 진입 5초 + REST 확인) |
| C 재시도 성공 (봉 미반영 후 정상 확정) | 3646회 시도 → 성공한 봉 다수 | 약 20~30초 (재시도 여러 번) |
| F1b NO_TRADE 확정 | 662 | 약 25~35초 (재시도 소진 후 ticks 조회) |

**지연 상한 산정**:

- **하한**: 케이스 A p95 = 15초. 즉 대부분의 봉은 15초 안에 확정된다.
- **중간 상한**: 케이스 B p95 = 15초. 대부분의 저유동성 봉도 15초 이내.
- **최상단**: 케이스 C p95 = 30초. 재시도 여러 번 후 확정되는 경우.
- **F1b NO_TRADE**: 35초. 다만 이 경우 매수 결정 자체가 없다.

**제안 지연 상한**: **60초** (= 1개 봉 간격).

- 근거: 케이스 A/B/C p95가 모두 30초 이내이므로 60초면 충분한 여유.
- 60초를 넘으면 대상 봉이 확정되지 않은 상태로 다음 봉이 도착. 다음 봉의
  실시간 판단에서 새 신호가 나올 수 있으므로 오래된 지연 주문은 취소하고 새
  판단에 위임하는 것이 안전.

### 2.3 흐름 (기 승인 §6 유지)

1. `[CLOCK-CLOSE]` → 실시간 평가 실행 (봉당 1회).
2. 평가 결과 매매 결정이 나오면 `fetch_confirmed_candle` 호출.
3. 확정이면 즉시 유효성 확인 → 발주.
4. 미확정이면 `_pending_orders`에 등록 후 대기.
5. 다음 CLOCK-CLOSE 시각에 확정 재판정 (다음 봉의 실시간 판단과는 별개).
6. 확정되면 유효성 확인 → 발주. 여전히 미확정이면 지연 상한 확인.
7. 지연 상한(60초) 초과 시 발주 취소, 로그와 감사 기록.

### 2.4 데이터 구조

```python
class PendingOrder:
    bar_ts: datetime           # 대상 봉
    decision: str              # 'BUY' or 'SELL'
    context: dict              # 관문 통과 시점의 스냅샷
    tentative_close: float     # 평가 시점 close (유효성 확인용)
    signal_condition: str      # 유효성 재확인할 조건 이름 (EMA_GC 등)
    created_at: datetime       # 등록 시각
    max_wait_sec: int = 60     # 지연 상한
```

`strategy_engine` 안에 `_pending_orders: List[PendingOrder]` 필드 신설.

### 2.5 유효성 확인 (재판정 아님)

- 대상: 대기 중이던 주문이 확정 조건을 충족한 시점.
- 방식: 확정된 종가로 원 신호 조건(예: EMA fast > EMA slow) **한 번만** 재계산.
- 관문(오염 차단, 재사용 대기, 포지션 제한, 필터)은 재실행하지 않음.
- 성립 → 발주. 불성립 → 발주 취소 + 감사 기록.
- 근거 사례: 2026-08-20 04:34 봉의 평가 종가 777원, 확정 종가 779원. 유효성
  확인은 779원 기준 EMA 재계산.

### 2.6 감사 컬럼 설계 (누락 조사 결과 반영 후 확정)

**임시안** (누락 조사 수정안 확정 이후 최종 결정):

`audit_buy_eval`에 다음 컬럼 추가:

- `pending_created_at TEXT` — 대기 등록 시각.
- `pending_resolved_at TEXT` — 확정 재판정 완료 시각.
- `validation_passed INTEGER` — 유효성 확인 결과(1: 통과, 0: 실패, NULL: 즉시 발주).
- `validation_reason TEXT` — 유효성 실패 사유(예: EMA fast < slow).
- `tentative_close REAL` — 평가 시점 종가.
- `confirmed_close REAL` — 확정 종가.

**주의**: 위 컬럼 추가는 1부의 감사 누락 수정안이 확정되면 함께 마이그레이션.
누락 조사 수정안이 audit 저장 경로 자체를 바꾸는 경우 이 컬럼 설계도 재검토
필요.

### 2.7 검증 계획 (세 겹)

**dry-run 병행 검증**

- 이번에 정비된 도구 재사용: `scripts/live_dry_run.py`(파라미터 자동 복사, 알림
  억제).
- 관측 시간: 활성 시간대 30봉으로 축소 가능. 판단 로직이 아니라 발주 지연만
  새 요소이기 때문.
- **통과 조건**: 발주 지연과 유효성 확인이 실제로 작동하는 사례를 최소 1건
  관측.
  - 케이스 B 안정화 대기 중 매수 결정이 나온 경우.
  - 케이스 C 재시도 중 매수 결정이 나온 경우.
  - 유효성 확인이 성립하여 발주된 사례 또는 불성립하여 취소된 사례.
  - 위 세 유형 중 최소 1건.

**배포 직후 30분 확인**

- 7단계 기동 로그.
- 지연 발주 로그 형식 정상 관측.
- Traceback/CRITICAL/POLLUTED 부재.
- 봉당 판단 1회 SQL 확인.

**24시간 실측**

- 실시간 판단 커버리지 (감사 + 로그 교차, 이번 산식 보완 규칙 적용).
- 총 지표 반영 커버리지.
- 지연 발주 관련 추가 지표:
  - 지연 주문 등록 건수.
  - 지연 상한 안에 확정된 비율.
  - 유효성 확인 통과율과 취소율.
  - 지연 주문 취소 사유 분포.
- 롤백 조건 5종 (WO-6 배포와 동일) + 유효성 확인 취소율 이상 신호.

### 2.8 롤백 정책

- 롤백 대상: WO-6 배포 상태(HEAD `b874ccc`).
- 롤백 절차: 옵션 A(revert 커밋 후 push, force 없음).
- 롤백 트리거:
  - WO-6 배포 시 정의된 5종 조건 그대로.

  - 추가: 지연 주문의 30%가 지연 상한 초과로 취소 → 지연 상한 재산정 검토(즉시
    롤백 아님).
