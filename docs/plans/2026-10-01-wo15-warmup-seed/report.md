## 세 질문의 답

1. **워밍업 시드**: 워밍업 13회 중 7회가 형성 중 봉을 시드에 넣었고, 11:40 봉(729→733)은 EMA60 을 −0.067원, EMA200 을 −0.020원 틀리게 시드했다. 이 오차는 아무 경로도 고치지 못하고(BACKFILL 은 복원으로 버리고, 부분 재계산은 데이터 부족으로 매번 실패) EMA 감쇠로만 줄어 1% 까지 EMA60 139봉·EMA200 461봉이 걸린다. 다만 크기는 SMA 시드 방식 자체의 오차(약 2.4원)의 약 3% 에 불과하다.
2. **REST 수신 부족**: 원인은 `fetch_candles_rest_full` 이 두 번째 배치의 `to` 를 **KST 문자열**로 넘기는데, pyupbit 0.2.34 는 이 문자열을 변환 없이 보내고 Upbit 는 시간대 없는 `to` 를 **UTC** 로 읽기 때문이다. 두 번째 배치가 9시간 뒤를 조회해 첫 배치와 겹치고(5분봉 107봉), 중복 제거 뒤 400→293~337, 201→200, 220→200 이 된다.
3. **다른 경로**: VERIFY(과거 봉 검증)는 같은 결함으로 `end_ts` 가 무시되고 범위가 "지금부터 200봉"으로 고정되어, 검증 대상 200봉 중 오래된 봉을 매번 "Upbit에 없는 timestamp" 로 건너뛴다(08-31 이후 140,582건). 재시도 경로는 실사용 2회(09-01, 성공 0회)뿐이다. a-2(첫 배치 `to` 적용)와 이번 `to` 시간대 결함은 같은 함수 같은 줄 근처라 **한 WO 에서 함께** 다루는 것이 맞고, 고치면 VERIFY 가 지금까지 건너뛰던 봉을 실제로 검증하게 되는 것이 가장 큰 위험이다.

## 2. 질문 2 — REST 요청 수보다 적게 받는 원인

### 2.1 원인 (코드)

- `core/rest_reconcile.py:236~249`(`to_kst_str` 생성 `:238`): 두 번째 배치부터 `to_kst_str = to.astimezone(Asia/Seoul).strftime("%Y-%m-%d %H:%M:%S")` 로 **시간대 표시 없는 KST 문자열**을 만든다.
- pyupbit 0.2.34 `get_ohlcv`(서버 venv `quotation_api.py:81~133`): 문자열 `to` 를 `pd.to_datetime` 으로 읽고 `#to = to.astimezone(datetime.timezone.utc)` 가 **주석 처리**되어 있어 그대로 `strftime` 해 Upbit 로 보낸다. pyupbit 스스로는 `to=None` 일 때 UTC 현재 시각, 다음 페이지는 `candle_date_time_utc` 를 쓴다. 즉 **pyupbit 는 시간대 없는 `to` 를 UTC 로 전제**한다.
- 따라서 두 번째 배치는 의도보다 **9시간 뒤**를 끝으로 조회한다. 그 구간은 첫 배치와 겹치고, `result.index.duplicated` 제거(`:313`)로 사라진다.

### 2.2 수치 대조

| 경우 | 계산 | 실측 |
|---|---|---|
| 조정 400 (5분봉) | 첫 배치 200 + 두 번째 배치 200 − 겹침(9시간 = 108칸 − 1, 무거래 봉 수만큼 줄어듦) | 11:50 `total=293` (겹침 107). 08-31 이후 5분봉 8,256회 전부 200 초과·400 미만(최소 293, 최대 337) |
| 워밍업 201 | 두 번째 배치 1봉(`to`=18:50 KST 의도 → UTC 로 읽혀 10-01 03:50 KST) → 03:45 봉 = 첫 배치에 이미 있음 | 13회 전부 `total=200` |
| VERIFY 220 | 두 번째 배치 20봉 전부 겹침 | 5분봉 8,255회·1분봉 2,980회 `220→200` |
| 1분봉 조정 400 | 9시간 = 540칸 > 200 → 두 번째 배치 전부 겹침 | 1분봉 시기 2,982회 중 2,615회 `400→200` |

- 대조 실험: 같은 Upbit API 에 `to` 를 UTC(`…Z`)로 넘겨 6회 연속 조회하자 **1,200봉 중복 0** (seed_drift.csv 계산용 원자료). `to` 시간대만 맞추면 요청 수만큼 받는다.

### 3.1 a-2 와의 겹침

- a-2 는 "첫 배치에도 `end_ts` 적용(`to=end_ts+봉 간격`)" 이다. 이번 결함(두 번째 배치 `to` 시간대)과 **같은 함수, 같은 `to` 문자열 생성 부분**이다. 첫 배치에 `to` 를 넣을 때도 UTC 로 넣지 않으면 같은 9시간 결함이 첫 배치에 생긴다. 따라서 둘은 따로 고칠 수 없고 한 변경으로 다뤄야 한다.
- a-2 를 적용하면 조정·VERIFY 에서 형성 중 봉이 사라진다. 워밍업은 `end_ts=None` 이라 a-2 만으로는 바뀌지 않는다(워밍업은 별도 처리 필요).

## 4. 처방 선택지 (비교만, 구현은 별도 승인)

### 4.1 REST `to` 시간대 (질문 2·3)

|---|---|---|---|
| **R1** | `fetch_candles_rest_full` 의 `to` 문자열을 UTC 로 만든다(`astimezone(UTC)`). 첫 배치는 지금처럼 `to` 없음 | 한 줄. 400·220·201 요청이 요청 수만큼 채워짐 | VERIFY 가 지금까지 건너뛰던 오래된 1~2봉을 실제로 검증 → 불일치가 있으면 **검증 실패 → 현재 봉 스킵**이 새로 생길 수 있음. 조정 수신이 ~400 으로 늘어 `[RECONCILE] 로컬 시작 이전 봉 제외` 의 n 이 커짐(WO-14 (b)가 잘라 내므로 BACKFILL 영향 없음). 워밍업이 201 을 받아 마지막 봉을 항상 버리게 되어, 형성 중 봉이 없을 때는 **확정 봉 1개를 버리고** 첫 조정이 그 봉을 BACKFILL(복원 때문에 지표에 영영 안 들어감) |
| **R2** | R1 + a-2(첫 배치에도 `to=end_ts+봉 간격`, UTC) | 조정·VERIFY 에서 형성 중 봉이 원천 차단. VERIFY 범위가 정확히 검증 대상과 일치. WO-14 (a) 필터는 안전망으로 남음 | 공용 함수라 영향 범위 넓음(워밍업·조정·VERIFY·재시도). Upbit `to` 경계(배타)·봉 간격 계산 검증 필요. Issue #8 계열 회귀 위험 — 단위·재현 테스트 필수 |
| R3 | 자체 페이지 반복을 없애고 `pyupbit.get_ohlcv(count=total, to=UTC)` 한 번 호출(pyupbit 가 UTC 로 페이지 반복) | 코드 축소, pyupbit 와 같은 시간 규약 | 배치별 로그·부분 실패 시 "이전 배치까지 사용" 동작이 사라짐. pyupbit 버전 의존 커짐 |

### 4.2 워밍업 형성 중 봉 (질문 1)

| 안 | 내용 | 장점 | 단점·위험 |
|---|---|---|---|
| **W1** | 마지막 봉 제거를 "개수 여유"가 아니라 **시각**으로 판정: `마지막 봉 시각 + 봉 간격 > 지금` 이면 형성 중이므로 제거. 요청은 `min_hist+1` 유지 | 형성 중일 때만 버리고, 확정 봉은 버리지 않음(R1 의 단점 해소) | 지금처럼 200 만 받는 상태에서 제거하면 199 < `min_hist` → `RuntimeError`(`engine/live_loop.py:1051`). **R1 또는 R2 가 먼저** 들어가야 함 |
| W2 | W1 + 요청 여유를 2~3봉으로 늘림 | R 안과 무관하게 W1 단독 적용 가능 | 지금 결함 상태에서는 두 번째 배치가 전부 겹쳐 여유분이 채워지지 않음 → 실제로는 R 안 없이는 효과 없음 |
| W3 | 첫 조정에서 워밍업 마지막 봉이 `changed` 면 그 봉 이전까지로 다시 시드 | 형성 중 봉뿐 아니라 워밍업 직후 바뀐 봉 전반을 바로잡음 | 다시 시드는 SMA 로 시작해 EMA 연속성을 끊고, `prev_ema` 초기화로 첫 실시간 봉 크로스 판정이 빠짐(Issue #11 계열). 위험 대비 효과(최대 0.067원)가 작음 |

### 4.3 권고 (선택지 비교 결과)

- **R2 + W1 를 한 WO 로**: `to` 시간대와 a-2 는 같은 줄이라 함께 고쳐야 하고, W1 은 R 안이 있어야 안전하다.
- 착수 전 필수 사전 점검: R 안 적용 시 VERIFY 가 새로 검증하게 될 "가장 오래된 1~2봉"이 지금 로컬 값과 일치하는지 **읽기 전용으로 먼저 측정**(불일치가 있으면 배포 직후 현재 봉 스킵이 생김).
- 영향 크기만 보면 형성 중 봉 시드(최대 0.067원)는 낮은 우선순위다. 실익은 R 안(수신 정상화·VERIFY 정상화·로그 140,582건 소음 제거)이 더 크다.
