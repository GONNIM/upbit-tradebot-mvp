# Mode Lock 로그인 가드 설계 기획안

**작성일**: 2026-07-03
**작성자**: 시스템 검증 결과 기반 (검증 대화: mcmax33 LIVE 진행 중 TEST 접속 시나리오)
**상태**: 초안 — 승인 후 구현 진행
**변경 대상**: `app.py`, `engine/engine_manager.py`, `pages/dashboard.py`

---

## 1. 배경·문제

### 1.1 발단 시나리오
mcmax33 아이디로 LIVE 모드 엔진이 서버에서 진행 중인 상태에서, 동일 아이디로 TEST 모드에 접속하고 "엔진 시작" 버튼을 눌렀을 때 서비스가 어떻게 동작하는지 검증하며 확인된 문제.

### 1.2 사용자 기대
> "LIVE 진행 중이면 같은 계정의 TEST 접속 자체가 차단되어야 한다."

실 자금이 매매되고 있는 상태에서 동일 아이디의 다른 모드 접속은 감사·조작 실수·상태 오염 리스크가 크므로, 시스템 차원에서 로그인·진입을 차단하는 것이 안전하다.

### 1.3 실제 코드
현재 코드에는 **로그인 시점의 모드 정합 가드가 존재하지 않는다.** 로그인은 성공하고, 엔진 시작 버튼을 누른 순간에만 `engine_manager`가 "이미 실행 중"으로 거부한다. 하지만 그 이전 단계에서 아래 부작용이 이미 발생·확정된다.

## 3. 설계 원칙

- **P1**: 실 자금 보호 최우선. 모드 불일치 상태에서의 잘못된 조작은 결과적 오작동보다 훨씬 큰 손실을 야기.
- **P2**: 사용자 실수(accidental stop, mode confusion)를 UI 레벨에서 사전 차단.
- **P3**: DB `last_mode` · 감사 로그 무결성 유지. 잘못된 mode 값이 저장되는 경로를 원천 봉쇄.
- **P4**: 최소 침습. 기존 인증(streamlit_authenticator)·엔진 매니저 아키텍처를 유지.
- **P5**: 조용한 차단 금지. 어떤 이유로 로그인·모드가 강제되는지 사용자에게 명시.

## 4. 옵션 비교

### 옵션 A: 로그인 시점 mode 강제 정합
로그인 성공 직후 `get_running_mode(username)`을 조회, 실행 중이면 사용자가 선택한 토글 값을 **무시하고** 실행 중 mode로 강제 override.

- 장점: 로그인 UX 흐름을 유지, 사용자는 "다른 mode를 볼 수 없음". 실 자금 보호 확실.
- 단점: 사용자가 의도적으로 mode 확인 목적으로 접속했을 때 혼란. UI에 명시적 안내 필요.

### 옵션 B: 대시보드 진입 시 리다이렉트·차단
로그인은 허용하지만 대시보드 렌더 직전에 mode 불일치 감지 → 다른 페이지(오류/안내)로 리다이렉트하거나 `st.stop()`.

- 장점: 로그인 로직에 손대지 않음.
- 단점: 이미 login 성공·session_state 초기화 진행 → `set_engine_status` 오염 위험은 그대로. 실질적 차단 시점이 늦음.

### 옵션 C: 엔진 시작 시점만 강화
`engine_manager.start_engine` 진입 시 `session mode ≠ _engine_mode[user_id]` 검사 → 거부하고 `set_engine_status` 호출 자체를 건너뜀.

- 장점: 침습 최소.
- 단점: 로그인·대시보드 진입은 여전히 허용 → 사용자 오인·감사 로그·UI 혼선 문제 그대로. 근본 해결 아님.

### 옵션 D (권장): 하이브리드 (A + C)
로그인 시점에 mode 강제 정합(A) + 엔진 시작 시점의 이중 방어(C).

- 장점: 실 자금 보호 + 감사·UI 무결성 + 방어 심화(defense in depth).
- 단점: 변경 지점 2곳. 하지만 각 변경은 국소적이고 명시적.

## 5. 권장안 상세 설계 (옵션 D)

### 5.1 신규 API
`engine/engine_manager.py`에 신규 메서드 추가:

```python
def get_running_mode(self, user_id: str) -> str | None:
    """
    해당 user_id로 실제 살아있는 엔진이 있으면 그 mode('LIVE'|'TEST')를 반환.
    없으면 None. 세션 mode를 참조하지 않는 순수 상태 조회.
    """
    key = _user_key(user_id, "")  # captured_mode는 키 생성에 미사용
    t = self._threads.get(key)
    if t is not None and t.is_alive():
        return self._engine_mode.get(key)
    return None
```

**중요**: 기존 `is_running`은 `current_mode()`(세션)를 호출하지만, 신규 `get_running_mode`는 세션 참조 없이 순수하게 실행 상태만 반환. 로그인 시점(=아직 mode가 확정되기 전)에도 안전하게 호출 가능.

### 5.2 로그인 시점 정합 (Option A)
`app.py:224` 이후, `init_db_if_needed` 호출 직전에 삽입:

```python
elif authentication_status:
    login_placeholder.empty()

    # ✅ [Mode Lock Guard] 실행 중 엔진 mode와 세션 mode 정합
    _selected_mode = st.session_state.get("mode", "TEST")
    try:
        from engine.engine_manager import engine_manager
        _running_mode = engine_manager.get_running_mode(username)
    except Exception:
        _running_mode = None

    if _running_mode and _running_mode != _selected_mode:
        # 선택 mode를 실행 중 mode로 강제 override
        st.session_state["mode"] = _running_mode
        st.session_state["_last_mode"] = _running_mode
        st.session_state["live_mode_toggle"] = (_running_mode == "LIVE")
        st.warning(
            f"⚠️ **모드 강제 전환** — 현재 `{username}` 계정으로 "
            f"**{_running_mode}** 엔진이 실행 중이어서 "
            f"선택하신 **{_selected_mode}** 대신 **{_running_mode}** 모드로 진입합니다.\n\n"
```

### 5.3 엔진 시작 시점 이중 방어 (Option C)
`engine/engine_manager.py:114-132` `start_engine`을 다음처럼 보강:

```python
def start_engine(
    self,
    user_id: str,
    test_mode: bool | None = None,
    restart_count: int = 0,
) -> bool:
    captured_mode = current_mode()
    tm = (test_mode if test_mode is not None else (captured_mode != MODE_LIVE))

    # ✅ [Mode Lock Guard] 이미 실행 중이고 mode가 다르면 명시 거부
    running_mode = self.get_running_mode(user_id)
    if running_mode and running_mode != captured_mode:
        msg = (
            f"⛔ [MODE-LOCK] 엔진 시작 거부: user_id={user_id}, "
            f"running={running_mode}, requested={captured_mode}. "
            f"기존 {running_mode} 엔진을 먼저 정지하십시오."
        )
        logger.warning(msg)
        try:
            insert_log(user_id, "WARN", msg)
        except Exception:
            pass
        return False  # ⚠️ set_engine_status 호출 전에 조기 반환 → last_mode 오염 방지

    # LIVE 모드 Reconciler 기동 및 미체결 로딩
    if captured_mode == MODE_LIVE:
        ...

    # 기존 last_mode 저장 로직
    try:
        from services.db import set_engine_status
        set_engine_status(user_id, True, last_mode=captured_mode)
    except Exception as e:
        logger.warning(f"[ENGINE-MANAGER] last_mode 저장 실패: {e}")

    return self._start_engine_internal(user_id, tm, restart_count, captured_mode)
```

**핵심 순서**: mode 불일치 감지 → `set_engine_status` 호출 이전에 `return False` → **DB `last_mode` 오염 원천 차단.** 하이브리드의 심층 방어(P1·P3) 실현.

### 5.4 대시보드 정지 버튼 보호 (부수적 강화)
`stop_engine`은 이미 `running_mode`를 정확히 사용하지만, 대시보드에서 "정지" 버튼을 누른 세션이 실제 실행 중 mode와 다르면 명시적 확인을 받는 것이 안전. 다만 옵션 A로 로그인 시점 정합이 이루어지면 실질적으로 이 상황은 발생하지 않음 → **본 기획안 범위 외로 두되 문서화만 함.**

## 7. 부작용·마이그레이션

### 7.1 UI 관점
- 사용자가 TEST 토글로 로그인해도 LIVE 엔진이 있으면 LIVE로 강제 진입 → **명시 warning 표시** → 사용자 오인 방지.
- Streamlit `session_state["live_mode_toggle"]`도 함께 업데이트 → 화면 상단 토글도 강제 상태 반영.

### 7.2 자동 재개 로직
- `pages/dashboard.py:385-437` 자동 재개는 `get_last_engine_mode(user_id)` 값에 의존.
- 5.3의 조기 반환으로 `last_mode` 오염이 사라짐 → 자동 재개는 오히려 **더 정확해짐**. 마이그레이션 필요 없음.

### 7.3 감사 로그
- 로그는 여전히 `insert_log(user_id, level, msg)`로 저장.
- mode 강제 전환 이벤트는 명시 로그(`[MODE-LOCK]` 태그)로 기록 → 사후 감사 추적 가능.

### 7.4 하위호환·롤백
- 신규 코드는 모두 조건부 추가. 기존 정상 흐름(같은 mode 로그인/시작)에는 무영향.
- 롤백은 세 지점(engine_manager 2곳 + app.py 1곳) `git revert`로 즉시 가능.

### 7.5 알려진 미커버 영역
- **Streamlit-authenticator 쿠키 다중 세션**: 브라우저 A·B가 서로 다른 쿠키로 동시 로그인하는 경우까지는 본 안이 커버(로그인 시점 mode 정합). 다만 완전한 "동일 계정 단일 세션"은 별개 논의(추후 확장 여지).
- **모드 변경을 위한 재로그인 안내**: warning 문구에서 "먼저 엔진 정지하고 재로그인"으로 유도. 자동 로그아웃까지는 구현하지 않음(사용자 판단 존중).

## 9. 롤아웃 순서

1. **Phase 1 · 로컬 구현**
   - `engine/engine_manager.py`에 `get_running_mode` + `start_engine` 가드 추가
   - `app.py` 로그인 후 mode 정합 로직 추가
