### 1-3′ 업비트 최대 기간 90일 (결정 ④)
- 사용자가 고르는 기간만 90일로 늘린다. 지금 MAX_DAYS 하나가 네 곳에서 쓰인다: 36(정의) · 108(요청 검사) · 386(보관 잘라내기) · 684(미리 받기). 108 은 90 으로, 684(미리 받기)는 30 그대로 둔다. `bt_ui.js:196` 검사도 90 으로 바꾼다.
- 보관 잘라내기(386)는 「max(30일, 그 파일에 마지막으로 들어온 사용자 요청 기간)」으로 바꾼다. 90일 요청은 백그라운드 작업이 되고(serve 631-633), 작업 결과는 파일로만 남는다(`_run` 576-579). 잘라내기를 30일로 두면 작업이 끝난 뒤 브라우저가 다시 읽을 때(bt_ui.js:105-114) 앞 60일이 없어 「받기 → 잘라내기 → 다시 받기」가 되풀이된다(verifier 2회째). 사용자 요청 기간은 파일 머리 정보(`_save`/`_load` 356-391 묶음)에 적고, 7일 동안 그 기간 요청이 없으면 30일로 돌아간다.
- 이 보관 기간 칸은 사용자 작업만 바꾼다. 미리 받기(684)와, 미리 받기를 사용자 작업으로 넘겨받는 경로(620-622)는 바꾸지 않는다. 그러지 않으면 엔진과 같은 종목·봉 단위에서 600초마다 30일로 다시 잘리고 60일을 다시 받는다.
- 저장소 크기 상한(30MB)은 받기 전에 예상 봉 수로 판단한다. 받은 뒤에 거절하면 요청을 헛되이 쓴다. 상한에 걸리면 다른 파일을 지우지 않고 그 요청을 거절한다. 미리 받기 저장의 오래된 파일 지우기(`_evict` 397-421)도 사용자 요청 기간이 30일보다 긴 파일은 지우지 않게 같은 규칙으로 맞춘다. 화면에 「기간을 줄이거나 봉 단위를 키워 주세요」를 보여 준다. 1분봉 90일 파일 크기는 로컬에서 재서 보고한다(추정 — 아직 안 잼).
- 시험: 「90일 작업이 끝난 뒤 다시 읽으면 바로 받기 상한(2회) 안에서 결과가 나온다(봉 경계를 지나면 1회 받는 것이 정상)」, 「미리 받기는 보관 기간 칸을 바꾸지 않는다」, 「30MB 를 넘는 요청은 거절하고 다른 파일은 그대로다」.
- 요청 수(1회 200개, 초당 4회 한도 그대로): 3분봉 90일 216회, 1분봉 90일 648회. 엔진 봉 경계 앞뒤 22초는 부르지 않으므로(candles.py:46-47·254-257) 1분 엔진이 돌 때 1분봉 90일은 최소 약 4.3분 걸린다. 응답 머리 Remaining-Req 의 남은 수가 4 이하이면 1초씩 더 쉬므로(candles.py:463-464·515) 실제는 더 길다(추정 — 로컬 실측 1회로 확인). 같은 IP 한도에 오래 노출되지 않도록 1분봉 90일은 메모리·시간 실측 1회로 그친다.
- 화면 대기 상한 `bt_ui.js:8` MAX_WAIT_MS 5분을 10분으로 늘린다. 진행률 표시를 붙인다.
- v2 서비스 메모리 상한은 150MB 이다(`deploy/tradebot-v2.service`). 1분봉 90일(129,600봉) 수집·응답 때 메모리를 로컬에서 재고, 100MB 를 넘으면 사용자에게 보고한다.
- 받기가 중간에 끊기면 받은 데까지만 쓰지 않고 오류로 끝낸다. 결과가 짧은 기간으로 오해받지 않게 하려는 것이다.
