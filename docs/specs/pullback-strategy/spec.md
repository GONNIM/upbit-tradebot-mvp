# PULLBACK 전략 (엔진 세 번째 전략) — 설계 문서

- 작성: 2026-10-21 · 상태: 확정 (2026-10-21 투자자 승인 — investor-notice-log #5)
- 관련: `docs/specs/v2-dashboard/spec.md` (신버전 대시보드, 전환 흐름 4.5·4.6)
- 규칙 원본: `docs/specs/MA60_200_GoldenCross_Pullback_Backtester_2610201820.html`의 `simulate()`(246~383행), `isFilterActive()`(229행), `computeEMA/SMA/Slope`(186~227행)

## 1. 목적과 이유

사용자는 신버전 대시보드의 백테스터에서 최적 설정을 찾아 저장하고, 실제 자동매매가 **백테스터와 같은 규칙으로** 돌기를 원한다(2026-10-21 결정).

지금 엔진의 EMA·MACD 전략은 이 규칙을 따를 수 없다. 차이는 세 가지다.
- 매수 시점이 다르다. 지금 엔진은 골든크로스가 일어나는 그 봉에서만 산다(`core/strategy_incremental.py:960-965`).
- 분할매수가 없다. 보유 중에는 추가로 사지 않는다(`:978`).
- 포지션 관리가 진입 1회만 전제한다(`core/position_state.py:223,273,291`).

그래서 기존 전략을 고치지 않고 세 번째 전략 `PULLBACK`을 새로 만든다. 기존 EMA·MACD 사용자와 지금 운용 중인 설정은 바뀌지 않는다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
- G1. 같은 확정 봉 데이터를 넣으면 `PULLBACK` 엔진의 매수·매도 판정(봉, 회차, 사유)이 원본 백테스터 `simulate()`와 같다.
- G2. 분할 포지션(회차, 평단, 첫 진입 시각, 눌림 상태)이 엔진 재시작과 BACKFILL 뒤에도 보존된다.
- G3. 전략 전환과 복귀를 D2 규칙(보유 중이면 청산 후 전환)으로 처리한다.

**비목표**
- EMA·MACD 전략과 그 필터(트레일링 스탑, 급등 필터, 약매수 차단, 정체 포지션)를 바꾸지 않는다. 이 필터들은 `PULLBACK`에 적용하지 않는다. 원본 백테스터에 없는 규칙이기 때문이다.
- 백테스터에 없는 매매 규칙을 추가하지 않는다.

**실패 조건**
- EMA·MACD 사용자의 매매 판정이 하나라도 달라진다.
- 일치 시험(6절)은 통과했지만 재시작한 뒤 회차나 평단이 틀어진다.
- 앱 주문(HTS) 감지, 묶인 수량 처리, 거절 가시화 같은 기존 보호 장치가 `PULLBACK`에서 빠진다.

## 3. 매매 규칙 (원본 `simulate()`를 그대로 옮김)

봉 i는 **확정 봉**이다(Issue #8). 판정은 봉 i 마감 시점에 한다. 매수는 "다음 봉 시가 체결" 가정에 대응해 봉 i 마감 직후 시장가로 주문한다. 각 봉에서 아래 순서로 평가하고, 어느 단계에서 동작이 일어나면 그 봉의 나머지 평가는 하지 않는다.

**지표**
- `maTrend` = MA(`ma60p`), `ma200` = MA(`ma200p`), `maPullback` = MA(`pullbackP`, 0 또는 빈 값이면 `ma60p`). 방식은 `maType`(ema/sma)을 따른다.
- EMA 시드는 첫 `period`개 종가의 단순평균이다. 이후 `k = 2/(period+1)`로 증분 갱신한다.
- `slope200[i] = (ma200[i] − ma200[i−slopeLB]) / |ma200[i−slopeLB]| × 100`

**활성 조건** `active(i)`: 아래를 모두 만족해야 한다.
- `maTrend[i]`, `ma200[i]`, `slope200[i]`가 모두 있음(없으면 비활성)
- `maTrend > ma200`
- `slope200 ≥ minSlope`
- `slopeDrop > 0`이고 `slope200[i−slopeLB]`가 **있을 때만** `slope200[i−slopeLB] − slope200[i] ≤ slopeDrop`. 과거 값이 없으면 이 조건은 통과로 본다(원본 229~244행).

**`golden(i)`** = `maTrend > ma200`. **`justCrossedGolden`** = `golden(i)`이고 직전 봉은 golden이 아님.

**평가 순서**
1. **데드크로스 청산:** 보유 중, `deadcross = yes`, `maTrend ≤ ma200`이면 전량 매도(사유 `DEADCROSS`). 원본의 청산가는 봉 i 종가다.
2. **TP/SL:** 보유 중이고 봉 시각 > 첫 **체결** 봉 시각일 때 평단 `avg` 기준으로 판정한다. 원본의 첫 체결 봉은 신호 봉 i의 다음 봉 i+1이므로, TP/SL 판정은 i+2봉부터 시작한다. 원본의 청산가는 TP·SL 가격 그 자체다.
   - `TP = avg × (1 + tp/100)`, `SL = avg × (1 − sl/100)`
   - 고가가 TP 이상이면 `TP`, 저가가 SL 이하이면 `SL`로 전량 매도한다. 한 봉에서 둘 다 닿으면 원본은 TP를 우선한다.
   - 실엔진도 봉 마감 때 확정 봉의 고가·저가로 판정한다(7.3 결정).
3. **골든크로스 1차 매수:** 아래를 모두 만족하면 1회차 매수(사유 `GOLDEN`), 눌림 상태 해제.
   - `buyOnGoldenCross = yes`
   - `justCrossedGolden`
   - 보유 회차 0
   - `active`
   - 회차 < `effMaxSplits`
4. **눌림목 매수:** 아래 조건이면 진행한다.
   - 조건: goldenOnly 모드가 아니고, 눌림목 회차 < `maxPullbackBuys`, `active`, 회차 < `effMaxSplits`
   - 저가 < `maPullback`이면 눌림 상태(armed)로 둔다.
   - armed이고 종가 > `maPullback`이면 매수한다(사유 `PULLBACK`). 같은 봉에서 armed되고 바로 매수될 수 있다. 매수 후 armed를 해제한다.
   - 비활성, goldenOnly, 눌림목 한도 도달 중 하나이면 armed를 해제한다.
   - **예외(원본 그대로):** 전체 회차가 `effMaxSplits`에 다 찬 경우에는 armed를 해제하지 않고 그대로 둔다(원본 `else if` 조건 밖). 일치 시험에 이 경우를 넣는다.
5. **청산 뒤:** 회차, 눌림목 회차, 첫 진입 시각, armed를 모두 초기화한다.

**분할 한도와 금액**
- goldenOnly 모드 = `buyOnGoldenCross = yes`이고 `maxSplits = 0`. 이 모드에서 `effMaxSplits = 1`이다.
- 1회 매수 금액 = 배분 기준 ÷ `effMaxSplits`. 배분 기준은 7.1을 따른다.
- 복리(`compounding = yes`)이면 새 거래를 시작하는 시점의 누적 자산을 배분 기준으로 쓴다.
  - 실엔진의 누적 자산 = 배분 기준(7.1) + `PULLBACK`으로 전환한 뒤 이 전략이 실현한 손익의 합.
  - 전환할 때마다 0부터 다시 센다. 앱 주문 손익은 넣지 않는다.
  - *(설계자 판단)*

**원본에 대해 확인된 사실 (검토 반영)**
- 원본은 데이터 시작 시점에 이미 골든크로스 상태여도 **1차 매수를 하지 않는다.** 이유는 다음과 같다.
  - golden이 처음 판정되는 봉은 `ma200`이 처음 생기는 봉이다.
  - 그 봉에서는 `slope200`이 아직 없어서 `active`가 false다.
  - 다음 봉부터는 `justCrossedGolden`이 false다.
  - 원본 주석("조회 시작 시점에 이미 골든크로스인")은 실제 동작과 다르다.
  - 따라서 실엔진도 시작 직후에는 사지 않고 **다음 골든크로스를 기다린다.** 이전 초안의 7.2 질문은 이 사실로 해소되어 삭제했다.
- 원본 데이터는 Binance(USDT)이고, `capital`도 USDT 단위다. 실엔진과 일치 시험은 Upbit(KRW) 데이터를 쓴다.
- `maxSplits = 0`이고 `buyOnGoldenCross = no`이면 원본은 영원히 매수하지 않는다. 설정 검증 단계에서 이 조합을 거부한다. *(설계자 판단)*

## 4. 설계

### 4.1 위치

- 새 클래스: `core/strategy_incremental.py`에 `IncrementalPullbackStrategy`를 두거나 새 모듈로 만든다(구현자 재량).
- 공개 인터페이스는 `on_bar`, `reload_conditions`, `set_interval_min`으로 기존 전략과 같게 맞춘다.
- 생성 분기: `engine/live_loop.py:884,905` 옆에 `strategy_type == "PULLBACK"` 분기를 추가한다.
- `engine/params.py`의 전략 유형 검증 목록에 `PULLBACK`을 추가한다. 기본값(`DEFAULT_STRATEGY_TYPE`)은 바꾸지 않는다.

### 4.2 설정 파일 `{user}_latest_params_PULLBACK.json`

원본 입력 이름을 그대로 키로 쓴다. 대시보드 spec 4.5와 같은 형식이다.

```
ticker, interval(minute1|minute3|minute5|minute60), maType(ema|sma),
ma60p, ma200p, pullbackP, slopeLB, minSlope, slopeDrop,
buyOnGoldenCross(bool), maxSplits(0~10), maxPullbackBuys(1~5),
tp(%), sl(%), deadcross(bool), compounding(bool),
capital(백테스트용만 — 실매매는 운용자산, 7.1), fee(% — 백테스트용, 실거래는 Upbit 실제 수수료)
```

- 값 범위 검증은 원본 `run()`과 같게 한다. `maxSplits`는 0~10, `maxPullbackBuys`는 1~5다.
- 엔진은 이 파일의 수정 시각을 감시해 다시 읽는다. 기존 `_maybe_reload_params` 경로(`engine/live_loop.py:531`)를 따른다.

### 4.3 증분 지표 상태

- 보관 항목:
  - `maTrend`, `ma200`, `maPullback`의 현재 값
  - SMA용 최근 `period`개 종가 버퍼
  - `ma200` 이력(`slopeLB`+1개)과 `slope200` 이력(`slopeLB`+1개)
  - 직전 golden 여부
- 전체 재계산은 금지한다(프로젝트 규칙). 봉마다 증분으로 갱신한다.
- **빈 봉:** Upbit는 거래가 없는 분의 봉을 만들지 않는다. 엔진은 기존 `fill_gaps_sync`로 빈 봉을 채운다. 원본은 MA와 `slopeLB`를 봉 개수로 세므로, 다음 세 곳에 **같은 빈 봉 채움 규칙**을 쓴다. 그래야 같은 규칙이 성립한다. *(설계자 판단)*
  - 대시보드 백테스터의 Upbit 출처
  - 일치 시험 fixture
  - 실엔진
- **워밍업:** 기존 긴 이력 증분 시드(WO-17 (S), 800봉)를 쓴다. 필요한 봉 수(`max(ma200p, pullbackP) + slopeLB×2 + 10`)가 800을 넘으면 늘린다. *(설계자 판단)*
  - 워밍업 봉에서도 3절 규칙을 끝까지 돌린다. 지표, `slope200` 이력, armed, 직전 golden 여부를 모두 갱신하고 **주문만 막는다.**
  - 워밍업이 끝날 때의 상태를 실시간 첫 봉으로 그대로 넘긴다. 원본에서 데이터가 워밍업 시작 봉부터 있었던 것과 같은 상태가 된다.
  - 워밍업 중에 생긴 매수 신호는 감사 로그에 `WARMUP`으로만 남긴다.
  - 기존 포지션이 없을 때는 워밍업 중의 가상 회차를 실시간으로 넘기지 않는다. 실제 포지션 상태는 4.4 기준이다.
- **BACKFILL:** 바뀐 봉부터 다시 재생한다. *(설계자 판단. 원본과 계속 일치시키기 위해서다)*
  - 봉마다 지표 상태와 분할 판정 상태의 스냅샷을 최근 N개(BACKFILL 최대 범위 이상) 링 버퍼에 둔다.
  - BACKFILL이 일어나면 바뀐 봉 직전의 스냅샷에서 출발해 증분으로 다시 재생한다.
  - 재생 범위는 BACKFILL 범위로 한정한다. 전체 재계산 금지 규칙의 범위 안이다.
  - 재생 중에는 주문을 내지 않는다(Issue #9 `is_backfill` 규칙).
  - 실제 포지션(수량, 평단, 회차)은 재생으로 바꾸지 않는다. 이미 낸 주문은 사실로 유지한다. Issue #11 원칙은 "재평가가 실제 상태를 오염시키지 않는다"로 지킨다.

### 4.4 분할 포지션 상태와 보존

- `PositionState`에 분할 추가매수를 넣는다. 추가할 때마다 수량과 원가를 누적하고 평단을 다시 계산한다.
  - 기존 단일 진입 경로(`apply_entry`, `open_position`)는 바꾸지 않는다.
  - 분할 경로는 `PULLBACK`에서만 쓴다.
- 분할 상태(회차, 눌림목 회차, 첫 진입 시각, 첫 진입 사유, armed, 직전 golden 여부, 거래 시작 시점의 배분 기준)는 사용자 DB의 새 테이블에 저장한다.
  - 엔진 재시작과 기동 재개(WO-12) 때 이 테이블에서 복원한다.
  - **DB 스키마 변경이다. 배포 승인 대상이다.**
- 지갑 동기화(WO-22)로 실제 수량과 평단을 확인한다.
  - 저장 상태와 지갑이 어긋나면 지갑을 우선한다. 어긋남을 `[PULLBACK-SYNC]` 로그와 감사 로그로 남긴다.
  - 어긋난 상태에서는 추가 분할매수를 하지 않는다. 청산 규칙(TP/SL/DC)은 계속 적용한다.

### 4.5 주문과 기존 보호 장치

- 매수는 시장가로 한다. 원본의 "다음 봉 시가 체결" 가정에 가장 가깝기 때문이다. 기존 「현재가 매수」 옵션은 `PULLBACK`에 쓰지 않는다.
- 매도는 시장가로 한다(기존과 같음).
- 그대로 적용하는 기존 장치:
  - 일시정지 플래그
  - 주문 전 차단 표시(WO-25)
  - 거절 가시화(WO-9)
  - 앱 주문 감지와 `hts_buy` 처리(Issue #17, WO-10·18)
  - 묶인 수량 구분
  - 최소 주문금액(5,000원) 검사
  - 거래 시간 제한 설정
- 1회 매수 금액이 최소 주문금액보다 작거나 가용 KRW가 부족하면 그 회차는 건너뛴다. 감사 로그에 사유를 남긴다. 원본은 이 제약을 계산에 넣지 않으므로 이 경우는 일치 시험에서 제외한다.

### 4.6 운용 중 파라미터 변경

- 포지션이 없을 때 바꾼 값은 다음 봉부터 적용한다.
- 보유 중에 바꾼 경우:
  - TP/SL/데드크로스는 즉시 새 값을 적용한다.
  - 회차 한도가 줄어 현재 회차보다 작아지면 추가 매수만 멈춘다. 이미 산 수량을 강제로 팔지 않는다.
  - MA 기간이나 방식이 바뀌면 지표를 다시 시드한다. 시드하는 동안 새 매수를 하지 않는다.
  - `ticker`나 `interval`을 바꾸면 4.7 전환과 같게 다룬다. 보유 중이면 「전환 예약」 상태로 두고, 기존 종목과 봉 단위로 청산을 마친 뒤 새 값으로 시작한다. hot-reload로 바로 바꾸지 않는다. *(설계자 판단)*
- 변경 사실과 적용 시점을 `audit_settings`에 남긴다.

### 4.7 전략 전환과 복귀 (D2)

- 전환 요청은 사용자 DB에 남긴다. 저장 항목은 대상 전략, 요청 시각, 직전 전략이다.
- 포지션이 없으면 즉시 전환한다. `{user}_active_strategy.txt`를 바꾸고 엔진을 다시 시작한다.
- 포지션이 있으면 「전환 예약」 상태로 둔다.
  - 기존 전략이 그 포지션을 끝까지 관리한다.
  - 청산이 끝난 봉 다음에 엔진이 전환한다.
  - 예약은 엔진 재시작 뒤에도 유지된다.
- 전환할 때 종목이나 봉 단위가 다르면, 기존 전략이 기존 종목으로 청산을 마친 뒤 새 종목으로 시작한다.
- 예약 중에는 **청산 규칙만 남기고 추가 매수를 하지 않는다.** 이미 정한 전환을 앞두고 노출을 늘리지 않기 위해서다. *(설계자 판단)*
  - `PULLBACK` → 복귀 예약: 데드크로스, TP, SL만 적용한다.
  - EMA/MACD → `PULLBACK` 예약: 기존 전략은 원래 추가매수가 없으므로 그대로 둔다.
- 예약은 신버전에서 취소할 수 있다.
- 복귀(`PULLBACK` → 직전 전략)도 같은 규칙을 따른다.
  - 직전 전략, 종목, 봉 단위는 전환할 때마다 기록한다.
  - 기록이 없으면 기본값으로 복귀하지 않는다. 사용자가 EMA나 MACD를 직접 고르게 한다. *(설계자 판단)*
- 모드(TEST/LIVE)별로 분리한다. 설정 파일, 분할 상태, 전환 예약 모두 기존 `_dry_` 접두사 규칙을 따른다. *(설계자 판단)*
- 전환, 예약, 완료를 감사 로그와 텔레그램 알림으로 남긴다. 알림에는 사용자가 할 일이 없음을 적는다.

## 6. 일치 시험 (G1 수용 기준)

- **입력:** Upbit 확정 봉 고정 데이터(fixture) 3세트 이상. 봉 단위 1분과 3분을 포함한다. 골든·데드·눌림 사례가 들어간 기간으로 고른다.
- **기준값:** 원본 `simulate()`를 Node로 실행해 얻는다(원본 JS를 바꾸지 않고 함수만 불러 씀). 출력은 매수·매도 목록(봉 시각, 회차, 사유)이다.
- **비교:** 같은 봉 배열을 `IncrementalPullbackStrategy`에 처음부터 한 봉씩 넣는다.
  - EMA 시드 시작점을 원본과 같게 맞춘다. 배열의 첫 봉부터 시드한다.
  - 판정 목록이 기준값과 **완전히 같아야** 한다.
- **조합:** 다음을 모두 시험한다.
  - `buyOnGoldenCross` yes/no
  - goldenOnly 모드(`maxSplits = 0`)
  - `maxPullbackBuys` < `maxSplits`
  - `slopeDrop` > 0
  - `deadcross` yes/no
  - `compounding` yes/no
  - `maType` ema/sma
- **비교 대상에서 빼는 것**(차이를 기록만 함):
  - 체결가(실거래 시장가 대 다음 봉 시가)
  - 수수료
  - 최소 주문금액과 잔고 부족으로 건너뛴 회차
- 재시작 시험: 같은 데이터 중간에서 엔진을 멈췄다가 DB 상태로 복원한 뒤 이어 넣어도 판정 목록이 같아야 한다.
- BACKFILL 시험: 중간 봉 하나를 바꿔 BACKFILL을 일으켜도 분할 상태가 오염되지 않고 실제 주문을 다시 내지 않아야 한다.

## 7. 사용자 결정 (2026-10-21 확정)

- 7.1 **실매매 배분 기준 = 사용자의 운용자산.** 운용자산은 로그인 때 정한 값이고, LIVE에서는 현재 설정된 운용자산이다.
  - 백테스터의 `capital` 입력은 시험용이다. 실매매 금액에는 쓰지 않는다.
  - 1회 매수 금액 = 운용자산 ÷ `effMaxSplits`.
  - 복리일 때는 3절의 누적 자산 규칙을 운용자산 기준으로 적용한다.
- 7.2 *(해소: 원본은 시작 시점에 사지 않는다. 다음 골든크로스를 기다린다. 3절 참조)*
- 7.3 **TP/SL 판정 시점 = 봉 마감 때.**
  - 확정 봉의 고가·저가로 판정한다. 한 봉에서 둘 다 닿으면 TP를 우선한다. 체결 봉은 판정에서 뺀다.
  - 판정 결과는 원본과 완전히 같다.
  - 청산은 봉 마감 직후 시장가로 하므로, 실제 청산가가 TP·SL 가격과 다를 수 있다. 이 차이는 체결가 차이로 관찰 항목에 둔다.
  - 6절 일치 시험은 TP/SL 판정까지 비교 대상에 넣는다.
