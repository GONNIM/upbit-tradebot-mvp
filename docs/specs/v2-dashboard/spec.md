## 1. 목적과 이유

지금 대시보드(Streamlit, `pages/dashboard.py` 2,890줄)는 화면을 한 번 바꿀 때마다 페이지 전체를 다시 실행한다. 이때 pyupbit 봉 조회, LIVE 잔고 조회, DB 쿼리 10여 건, Altair 차트 2개가 매번 함께 돈다. 그래서 무겁고, 모바일에서 쓰기 불편하다.

신버전은 가벼운 HTML 화면으로, 필요한 수치만 주기적으로 받아 갱신한다. 원본 백테스터를 메뉴로 넣고, 거기서 저장한 설정으로 실제 자동매매가 돌게 한다. 이때 엔진 전략은 P3의 `PULLBACK`이다.

구버전은 그대로 남긴다. 사용자는 로그인 후 입장 화면에서 구버전과 신버전 중 하나를 골라 들어간다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
- G1. 입장 화면에서 구버전과 신버전을 골라 들어간다.
- G2. 신버전에서 상태, 자산, 포지션, 거래, 신호, 차트, 로그를 가볍게 본다. 모바일 412px 폭을 기준으로 한다. PC(641px 이상)는 「기본 기능 블록 + 원본 백테스터」 한 페이지다(4.3, 2026-10-25).
- G3. 원본 백테스터의 기능을 빠짐없이 신버전 메뉴에서 쓴다. 같은 입력이면 원본과 같은 결과가 나와야 한다.
- G4. 백테스터 설정을 사용자별로 저장하고, 확인을 거쳐 실제 엔진에 적용한다.
- G5. 신버전에서 엔진 전략을 `PULLBACK`으로 전환하거나 기존 전략으로 복귀한다(결정 D1~D4).

**비목표**
- 구버전 화면과 기능을 바꾸거나 없애는 일. 예외는 입장 버튼 추가(4.1)와 PULLBACK 표시·차단(4.6)이다.
- EMA·MACD 전략 로직을 바꾸는 일.
- Binance에서 실제로 매매하는 일. Binance는 백테스트 데이터로만 쓴다.
- 서버 계산 백테스트. 백테스트는 원본처럼 브라우저에서 계산한다.

**실패 조건** — 기능이 동작하더라도 아래 중 하나라도 해당하면 실패로 본다.
- 신버전 페이지에 입장만 했는데 실매매 규칙이 바뀐다.
- 신버전 서비스(`tradebot-v2`)의 오류·지연·메모리 사용 때문에 엔진 서비스(`tradebot`)가 멈추거나 늦어진다.
- 신버전의 엔진 제어 때문에 엔진이 두 개 뜨거나 같은 주문이 두 번 나간다.
- 구버전 사용자 흐름(입장, 설정, 강제 매매, 감사 로그)이 하나라도 회귀한다.
- 백테스터 결과와 실제 엔진의 판정이 같은 봉 데이터에서 다르다. 이 판정은 P3 일치 시험으로 한다.

| E18 | 신버전은 root로 실행하고 systemd로 범위를 막는다: `ProtectSystem=strict`, `ProtectHome=read-only`(strict 만으로는 `/root` 가 쓰기 가능으로 남음 — systemd 249, 2026-10-25 배포 D5 실측), 쓰기 허용 `ReadWritePaths=-`는 `services/data/` 폴더(WAL 읽기의 `-shm`, `v2hist`의 `-journal` 생성에 필요)와 `{user}_latest_params_PULLBACK.json`(빈 파일 선생성, 제자리 쓰기)만, `InaccessiblePaths=-`는 `.env`·`.streamlit/secrets.toml`·`credentials.yaml`, `NoNewPrivileges`, `UMask=0077`, 후보로 `CapabilityBoundingSet=`(빈 값)·`AmbientCapabilities=`(빈 값). 허용 목록에 계정을 더할 때마다 빈 PULLBACK 파일 선생성·유닛 수정·`daemon-reload`·`tradebot-v2` 재시작이 필요하다. 남는 위험: (1) 엔진 프로세스 환경변수(업비트 키 포함)는 같은 root라 `/proc`로 읽힐 수 있다. 권한 집합을 비우면 막힐 수 있으나 서버 실측 전까지 미확인이다(A17에서 실측) (2) 실매매 DB 파일 쓰기는 폴더 허용 때문에 systemd로 막지 못한다. 둘 다 코드(읽기 전용 연결, 금지 import·경로 검사)로 막는다. **2026-10-25 예외: 폴더 쓰기 허용 아래에서 `v2.db.set_paused` 가 `mode=rw` 로 실매매 DB 를 한 번 연다(위 (2)의 실제 사용). 쓰기 SQL·테이블·연결 위치는 시험으로 고정하고(A19), 유닛 안 쓰기 가능 여부는 탐침 `live-db-write-lock`(`BEGIN IMMEDIATE`→`ROLLBACK`)으로 본다(A20)** |
| E19 | (E14 판정 범위) 백테스트 속도는 **계산 시간**(백테스트·스윕)으로 판정한다. 같은 입력·같은 브라우저에서 원본·이식본 각 3회, 중앙값이 원본 대비 +20% 이내. 데이터 받기는 시간 대신 「요청 수·받은 봉 수가 원본과 같음」으로 판정하고 시간은 기록만 한다 |

## 4. 설계

### 4.1 구조

```
브라우저 ─ https://orionhunter7.cafe24.com (nginx 443, 기존 인증서)
   ├─ /     → :8501 Streamlit (구버전)
   └─ /v2/  → 127.0.0.1:8502 신버전 (API + 정적 파일)
```

- 신버전은 별도 systemd 서비스 `tradebot-v2`로 돈다. `tradebot.service`와 서로 시작·정지·재시작이 묶이지 않는다.
  - 신버전을 즉시 끄는 방법은 `systemctl stop tradebot-v2`이다. 엔진은 영향을 받지 않는다.
  - 신버전 배포는 `tradebot-v2`만 재시작한다. `tradebot`(엔진)은 재시작하지 않는다. 예외: 1차 배포는 입장 버튼(`app.py`) 반영을 위해 `tradebot`을 1회 재시작한다(E1).
  - 두 서비스는 같은 작업 트리를 쓴다. 신버전만 배포할 때는 `git diff --stat <서버 HEAD> <배포 HEAD>`가 `v2/`·문서뿐인지 먼저 확인한다. 엔진의 늦은 import가 섞인 코드를 읽지 않게 하기 위해서다.
  - 유닛에는 실행 계정과 보호 설정(E18), `MemoryMax`, `OOMScoreAdjust`(엔진보다 먼저 종료되도록), `Nice`/`CPUWeight`를 둔다. 업비트 키가 든 `EnvironmentFile`은 넣지 않는다.
  - 서버 프레임워크는 구현 계획에서 정한다(기존 설치 패키지 우선). 새 의존성은 `requirements.txt`에 버전을 고정해 넣는다.
- 엔진 메모리(`engine_manager` 싱글턴)를 읽지 않는다. 엔진 상태는 DB에서 읽는다(E17). 엔진 제어는 4.7의 방식으로만 한다. 예외(2026-10-25 1025-21 가): 기본 기능 블록의 「트레이딩 엔진 상태」는 엔진 프로세스(`scripts/tradebot_boot.py` 감시 스레드)가 5초마다 내보내는 `services/data/.engine_alive.json` 을 읽는다 — 신버전이 엔진 메모리를 직접 읽지는 않는다.
- DB·설정은 신버전 전용 경량 모듈로 읽는다(E2). 읽기는 `file:...?mode=ro` URI로 연다. DB 파일이 없으면 만들지 않고 거부한다. 조회에는 LIMIT과 시간 제한을 둔다.
- 쓰기는 설정 파일, 신버전 이력 파일 `v2hist_<user>.db`(E15), 4.7의 엔진 제어 요청 기록뿐이다. 각 쓰기는 짧은 트랜잭션 하나로 한다. 실매매 DB에는 1차에서 쓰지 않는다. **예외 한 칸(2026-10-25 사용자 결정 1025-19 1 가)**: 「매매 중지/재개」는 구버전과 같이 실매매 DB 의 `users.trading_paused` 한 칸과 `logs` 한 줄만 쓴다. 쓰기 함수는 `v2/db.py set_paused` 하나, SQL 은 `INSERT INTO users … ON CONFLICT DO UPDATE`·`INSERT INTO logs` 두 문장뿐이며 `BEGIN IMMEDIATE` 한 트랜잭션에 묶는다(시험으로 고정, A19).
- 신버전 코드에서 업비트 API 호출 경로를 두지 않는다(D8). 시험으로 고정한다.
- nginx에 `location /v2/ { proxy_pass http://127.0.0.1:8502; }` 한 블록을 추가한다. 서버 설정 변경이므로 배포 승인 범위에 넣는다.
- 8502는 `127.0.0.1`에만 연다. 외부에서 직접 접근할 수 없다.
- systemd 유닛 파일 추가와 `enable`은 서버 설정 변경이므로 배포 승인 범위에 넣는다.

### 4.2 인증

- 입장 버튼이 짧게 유효한(60초) 1회용 서명 토큰을 만들어 `/v2/?t=`로 넘기고, 신버전은 자체 세션 쿠키(`HttpOnly`, `Secure`, `SameSite=Lax`, path `/v2/`)를 발급한다(E6).
- 구버전 쿠키 재사용은 하지 않는다. 서버 설정상 구버전이 쿠키를 발급하지 않는다(`secrets.toml` environment="local", `credentials.yaml` expiry_days 0).
- 토큰 서명 키는 새 비밀 파일(권한 600, 사본 금지, 정기 점검 대상)에 둔다. 토큰이 nginx 접근 로그에 남는 점은 계획서 Review Focus에 넣는다.
- 「구버전으로」 링크로 돌아가면 구버전에 다시 로그인해야 한다. 화면 문구에 이 사실을 적는다.
- 모든 API는 세션의 `user_id`로만 동작한다. URL 파라미터로 받은 `user_id`는 믿지 않는다.
- 모드(TEST/LIVE)는 입장 시점의 구버전 세션 값을 토큰이나 쿠키에 담아 넘긴다. 신버전 화면 상단에 항상 표시한다.

### 4.4 백테스터 메뉴

- 원본 백테스터의 기능 전부를 이식한다.
  - 입력 30개(`<input>` 24 + `<select>` 6 — 메인 19, 스윕 10, 차트 1) *(2026-10-22 정정: 이전 「24개」는 `<select>`를 빼고 센 값)*
  - 「데이터 가져오기 + 백테스트」
  - 파라미터 스윕(TP·SL·분할 횟수 범위, 정렬 기준 4종)
  - CSV 4종(거래 로그, 주간, 월간, 스윕)
  - 차트(확대·축소, 다시 그리기, 표시할 봉 수)
  - 결과 요약, 분할 단계별 누적 통계, 주간·월간 표(한국시간)
  - 전략 설명 접기
- 계산 로직은 원본 JS를 그대로 옮긴다. 이식 후 같은 입력(Binance, 같은 기간)에서 원본과 결과가 같아야 한다.
- 데이터 출처: P1·P2에서는 Binance(원본 그대로)만 둔다(R7). 출처 선택 칸은 「업비트 (KRW) — 준비 중」으로 표시하고 누를 수 없게 한다.
- Upbit 출처(P3에서 연다): 엔진이 이미 받은 확정 봉의 기록을 쓴다. 신버전은 업비트를 부르지 않는다(D8). 서버 DB에는 봉(OHLC) 테이블이 없으므로(2026-10-22 확인, `candle_cache` 포함) **엔진에 확정 봉 기록 기능을 새로 만든다.** 이 기능은 P3 범위이며 엔진 변경이다. 엔진이 기록하는 종목·봉 단위, 기록 시작 이후 기간만 시험할 수 있다. 빈 봉 규칙은 엔진과 같게 둔다(P3 spec 4.3).
- 설정 저장(4.5)은 **Upbit 출처일 때만** 「이 설정으로 동작」을 고를 수 있다. Binance 결과는 「저장만 하기」만 가능하다. 실매매 거래소와 다른 데이터로 찾은 값을 바로 실매매에 적용하지 않기 위해서다. 따라서 2차 공개(「이 설정으로 동작」)는 Upbit 출처가 열린 뒤에 한다.

### 4.5 설정 저장과 적용 (D4)

- 저장 파일은 `{user}_latest_params_PULLBACK.json`이다(E7). 경로 규칙은 기존 `engine/params.py`의 `scoped_params_path`를 따른다. 신버전은 이 이름만 쓸 수 있고, EMA·MACD 파일은 쓰지 않는다.
- 형식은 P3 spec 4.2의 키를 그대로 쓴다. 엔진은 이 파일을 읽어 동작한다.
- 저장할 때마다 신버전 경량 모듈이 `v2hist_<user>.db`에 이력을 남긴다(E15). 기존 `record_snapshot`은 `config`를 import 하므로 쓰지 않는다(E2). 열 구성은 `settings_history`와 같게 하고(`saved_at` KST ISO, `app_version`, `params_json` 원문 등) 출처 이름은 `v2_backtester`로 한다.
- 「저장」을 누르면 확인 창을 띄운다.
  1. 현재 상태: 동작 중인 전략(EMA/MACD/PULLBACK), 모드(TEST/LIVE, 크게 표시), 엔진 동작 여부, 보유 포지션(수량, 평단).
  2. 선택지:
     - 「저장만 하기」: 파일과 이력만 쓴다.
     - 「이 설정으로 동작」:
       - 전략이 이미 `PULLBACK`이면 파일만 저장한다. 엔진은 기존 hot-reload 경로(파일 수정 시각 감지)로 새 설정을 다시 읽는다.
       - 전략이 EMA/MACD이면 D1·D2 전환 흐름(4.6)으로 넘어간다.
       - 엔진이 정지 상태이면 「엔진 시작」 여부를 한 번 더 묻는다.
- 운용 중 파라미터를 바꿀 때의 규칙(보유 포지션의 회차와 평단을 유지할지 등)은 P3 spec 4.6을 따른다.
- 백테스터에 없는 운용 설정은 신버전 운용 메뉴(P4)의 「운용 설정」에서 바꾼다. *(설계자 판단)* 이유는 D3로 구버전 설정 화면이 잠기기 때문이다.
  - 거래 시간 제한(`enable_trading_hours`, 시작·종료 시각, 시간 외 매도 허용): `{user}_latest_params_PULLBACK.json`에 함께 저장한다.
  - 일시정지: 기존 DB 플래그를 그대로 쓴다.
  - 엔진이 쓰는 `LiveParams` 필수 필드(`cash`, `commission` 등)는 로더가 PULLBACK 파일과 7.1 배분 기준으로 채운다. 기존 EMA 파일은 읽지 않는다.
- TEST 모드에서도 「이 설정으로 동작」을 허용한다. 파일과 상태는 기존 `_dry_` 접두사 규칙으로 LIVE와 분리한다. *(설계자 판단)* *(2026-10-22 확인: 코드에 `_dry_` 규칙이 없다 — `scripts/live_dry_run.py`의 별도 user 이름 관례뿐이고 TEST/LIVE 는 같은 DB를 쓴다. P4 계획에서 분리 방식을 다시 정한다)*

### 4.6 전략 전환·복귀 (D1·D2·D3)

- **D1:** 신버전에 입장하면 상단에 현재 전략을 보여 준다. 전략이 `PULLBACK`이 아니면 「백테스터 규칙으로 전환」 버튼을 함께 보여 준다. 이 버튼을 누르고 확인 창에서 확인해야만 전환을 시작한다.
- **D2:** 전환할 때 포지션이 없으면 즉시 `{user}_active_strategy.txt`를 `PULLBACK`으로 바꾸고 엔진을 다시 시작한다. 포지션이 있으면 상태를 「전환 예약」으로 둔다. 기존 규칙으로 청산이 끝난 뒤 엔진이 자동으로 전환한다. 동작 상세는 P3 spec 4.7에 있다.
- 신버전 운용 메뉴에 「기존 전략으로 복귀」 버튼을 둔다.
  - 복귀 대상은 전환 직전의 전략, 종목, 봉 단위이며 기록해 둔다.
  - 기록이 없으면 사용자가 EMA나 MACD를 직접 고른다. 기본값으로 복귀하지 않는다.
  - 복귀에도 D2와 같은 규칙을 적용한다.
- 「전환 예약」 중에는 신버전에 「예약 취소」 버튼을 둔다.
- D3 잠금은 `PULLBACK` 운용 중일 때와 **전환 예약 중일 때(어느 방향이든)** 모두 적용한다. *(설계자 판단)*
- 신버전의 「엔진 시작」은 입장 시 넘겨받은 모드로 요청한다. 이미 다른 모드로 도는 엔진이 있으면 엔진 쪽에서 요청을 거부하고, 신버전은 그 사실을 표시한다. 기존 Mode Lock Guard(`engine/engine_manager.py`)는 엔진 프로세스 메모리만 보므로 신버전 프로세스에서 쓸 수 없다. 판정은 엔진 프로세스 안에서 한다(4.7). *(설계자 판단, 2026-10-22 별도 프로세스 기준으로 고침)*
- **D3:** 구버전 변경은 다음 두 가지에 한정한다.
  - `pages/dashboard.py`, `pages/set_config.py`, `pages/set_buy_sell_conditions.py` 상단에 「PULLBACK 운용 중 — 신버전에서 관리」 배지를 표시한다.
  - 설정 저장, 전략 변경, 엔진 시작 버튼을 비활성화한다.
  - 강제 매도와 엔진 정지는 비상 개입용이므로 막지 않는다(프로젝트 접힘 화이트리스트 원칙과 일치).
- 전환과 복귀 이벤트는 감사 로그에 남긴다. 이 이벤트는 손익 집계에 넣지 않는다.

### 4.7 엔진 제어 — 별도 프로세스 기준 재설계 (P4)

- **예외(2026-10-25, 1025-19 1 가)**: 일시중지·재개만은 요청 기록 방식이 아니라 구버전과 같은 상태 직접 쓰기다. `users.trading_paused` 를 바꾸면 엔진이 봉마다 읽어 BUY·SELL 실주문을 건너뛴다(`core/strategy_engine.py:1086-1095`). 이미 걸려 있는 주문은 취소되지 않고, 미체결 지정가 매수가 시장가로 바뀌는 처리(`convert_unfilled_limit_buy`)는 이 게이트를 거치지 않아 계속될 수 있다. 엔진 시작·정지·전환·강제 매매는 아래 설계대로 P4 에서 한다.

- 신버전(`tradebot-v2`)은 엔진 함수(`start_engine`, `stop_engine` 등)를 직접 부르지 않는다. 신버전 프로세스에서 부르면 신버전 안에 두 번째 엔진이 떠 같은 주문이 두 번 나갈 수 있다(검증 보고 지적 14).
- 신버전은 제어 요청을 DB나 파일에 기록만 한다. 엔진 프로세스(`tradebot`)가 그 요청을 읽어 자기 안에서 실행하고 결과를 기록한다. 요청 형식, 읽는 주기, 중복·만료 처리, 결과 표시는 계획서에서 정한다.
- 엔진 쪽 실행 경로는 Streamlit 세션 값 없이 동작해야 한다. `engine/engine_manager.py:357`(`st.session_state`의 `strategy_type`), `:105`·`:250`(`current_mode()`)은 세션 밖에서 값이 없으므로, 엔진 쪽 실행 경로가 모드와 전략을 인자로 받게 한다. 인자가 없으면 지금처럼 세션 값을 쓴다.
- 이 변경은 구버전 동작을 바꾸면 안 된다. 기존 회귀 시험 전부와 WO-12 기동 재개 시험으로 확인한다.
